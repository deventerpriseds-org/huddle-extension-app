**Created:** 2026-07-26. **Base at open:** `a832adde` (old). **Files touched:** `src/features/huddle/components/BoardView.tsx` (+56/-17), `.claude/actions.md` (+27/-1, an unrelated tracking-doc note about ACT-4/a "message-driven remote team" vision — not part of the feature).

2026-09-12) already contains: `onStatus` prop (lines 524/597/628/638), `curColKey`/`curCol` (683-684), the

**(5) Recommendation: CLOSE-SUPERSEDED.** The exact capability (per-card status dropdown, writing through

landed), and the repo's own record says it still has stated future value (seed content for the OpenAI
`file_search` vector stores, which per that same memory entry are provisioned/bound but still empty — no
`POST /v1/files` exists anywhere in the repo yet).

**(3) Merge conflict against current origin/main:** Practically yes, though not from real content overlap.

repo — there is no common ancestor) reports **add/add conflicts on ~30 unrelated files** (`routing.ts`,
`store.ts`, `tasks/*.server.ts`, `routeTree.gen.ts`, etc.) purely because git has no shared base to

hand-applied rebase/cherry-pick of just this PR's diff onto current main is very plausible even though a
GitHub "Merge pull request" button click almost certainly is not, given the disjoint history.

**(4) Staleness:** 56 days old, base predates the repo's squash-rewrite roots. `huddle.functions.ts` has
grown roughly 3x since (the anchor lines now sit at ~2567/3268 vs ~1067/1379 in the PR's diff) — the file
around the insertion point has been heavily rewritten, though the two exact anchor lines this PR needs

**(5) Recommendation: NEEDS-HUMAN-CALL.** This is not a simple supersede/stale case: the repo's own memory
already ruled it's a distinct, still-valuable capability, explicitly deferred merging it (not for the
current "intake" ACT-61) while explicitly declining to close it ("don't delete it either"). It also
directly touches **live agent prompt assembly** (`huddle.functions.ts` `appSystem`/`stableInstructions`),
which this repo's CLAUDE.md marks as a hard rule ("Agent prompts are ADDITIVE-ONLY... any subtractive
prompt edit requires explicit user sign-off") — this PR is additive so it doesn't violate that rule, but
changing live prompt assembly is exactly the kind of change CLAUDE.md says needs a stated plan +
go-ahead before merging/deploying. A human should decide: (a) merge now as always-on seed knowledge, (b)
hold it and instead feed the same 15 packs through the now-built memory-intake path (ACT-61) as
`agent`-scoped chunks — arguably the better fit and avoids a second, prompt-baked content mechanism — or
(c) close it in favor of (b). Given "extend, don't duplicate" is also an org-wide hard rule and ACT-61's
intake mechanism now exists, option (b)/(c) look more consistent with that rule than a straight merge, but
that's a content-strategy call for the user, not a mechanical one.
