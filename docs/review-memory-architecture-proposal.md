# Adversarial Review: Lane-Scoped Memory Architecture Proposal

Reviewer: Claude (independent design review, read-only)
Date: 2026-09-22
Repo: huddle-extension-app

This document verifies each "confirmed fact" in the proposal against the actual
code, then evaluates the proposed Tier 0/1/2 architecture for lane-scoped

## 1. Verification of each "confirmed-today fact"

`src/features/huddle/lib/identity/user-context.server.ts` defines `identity.user_context` exactly as described (`goals, ventures, positioning, audience, income_targets, notes`, keyed by email with a `user_id` fallback/dedup path). `renderExecutiveContext()` (line 128) returns `""` when nothing is set and otherwise renders a "Who you serve" block. Confirmed both call sites in `huddle.functions.ts`: line 1815-1817 and line 7089-7091. The second site is indeed the delegated **worker sub-turn** path (`payload.worker`, around line 7060-7107) — confirmed it calls `getUserContext`/`renderExecutiveContext` for `execBlock`, feeding `workerPrompt(...)`. Worth noting: the worker path's tool surface is only `tavily_web_search` + `create_artifact` (lines 7112-7160ish) — it has **zero** RAG/memory auto-retrieval of any kind, not even Tier 0's sibling mechanisms. So Tier 0 reaches workers; nothing that looks like Tier 1 does today, and the proposal doesn't change that (reasonable, but should be stated as an explicit non-goal rather than left implicit).

**Fact 2 (voice gap) — CONFIRMED.** `assembleRealtimeInstructions()` in `realtime-tools.server.ts` (lines 114-143) builds `base + memoryBlock + VOICE_HOUSE_STYLE`. `memoryBlock` comes only from a raw `azurePgStore.searchChunks({query: q, k: 5, mode: "shared"})` call keyed on `opts.memoryQuery` — no `getUserContext`, no `renderExecutiveContext`, no lane-boost, no `winner.domains`/`themes` anywhere in this file. Confirmed absent. This means the proposal's Tier 0 fix (filling in the empty Executive Profile fields) still does **not** reach voice calls — that's a pre-existing, separately-known gap the proposal doesn't claim to fix, but it should be stated plainly that filling in the profile fields does nothing for the voice surface.

**Fact 3 (`rag_chunks` schema, `scopeClause`, defaults) — CONFIRMED, with important nuance the proposal omits.**
- `azure-pg.server.ts` line 127-148: `rag_chunks` has `scope rag_scope` (enum `'agent'|'global'`), `agent_id TEXT`, `author_agent_ids TEXT[] DEFAULT '{}'` added via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (line 138), GIN-indexed at line 145-148 (`rag_chunks_authors_idx`).
- `scopeClause()` (line 487-506) confirmed exactly: `"private"` → `scope='agent' AND agent_id=$AGENT` only (global explicitly excluded); default/`"shared"` path → `scope='global' OR (scope='agent' AND agent_id=$AGENT)`; `"readonly-shared"` → `scope='global'` only.
- `RagConfigSchema.sharing` defaults to `"shared"` (agent-backends.ts line 17), and both concrete default objects (lines 38-44, ~150) also set `sharing: "shared"`. So yes, every agent's default candidate pool already includes the entire `scope='global'` table plus its own agent-scoped rows.

**Nuance the proposal misses: `runBootstrap` is NOT automatic.** The header comment at line 216-219 is explicit: "Explicit schema bootstrap... **Never called implicitly by store methods** — the user runs this from Agent Settings → Memory DB." CLAUDE.md confirms independently: "memory does NOT auto-bootstrap (explicit `runBootstrap` only)." So adding `domains TEXT[]` via the same `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` pattern is schema-safe in the sense that it won't break existing rows/queries, but it is **not** "live the moment code deploys" the way identity/tasks tables are — someone has to click "Run bootstrap" in Settings after the code change ships, or any code that assumes the column exists (writes, or a `SELECT domains` in `searchChunks`) will 42703 until that happens. The proposal should say this explicitly rather than imply automatic rollout.

**Dedup-key risk not addressed by the proposal.** `CHUNK_DEDUP_KEY` (line 87) = `scope, coalesce(agent_id,''), coalesce(source,''), md5(text), length(text)` — deliberately does **not** include `author_agent_ids`, and the code comments explain exactly why `metadata`/`embedding` are "FIRST WRITER WINS... not in the DO UPDATE" (lines 556-561), while `author_agent_ids` **is** explicitly merged in the `ON CONFLICT DO UPDATE` (lines 594-599, array union with a `<@` guard). If `domains` is added the same way `author_agent_ids` was, but the ON CONFLICT SET clause is **not** also extended to merge `domains`, then domains tags will silently follow the "first writer wins" behavior: re-running the ingestion script (e.g., after fixing a typo in the memory dump, or re-tagging a domain) against text that already exists in the table (same scope/agent_id/source/text) will **not** update the stored domains — the existing row's (possibly missing or stale) domains value wins. This is a concrete, non-obvious implementation requirement the proposal doesn't call out: extending `writeChunk`'s `ON CONFLICT DO UPDATE` to merge `domains` (array union, same pattern as `author_agent_ids`) is necessary, not optional.

**Fact 4 (sharing = privacy toggle, not lane scoping) — CONFIRMED.** `SettingsSheet.tsx` lines 848-861: `Switch` bound to `rag.sharing`, label "Shared memory," copy "On = this agent reads and writes shared memory. Off = private to this agent." Exactly as described. The proposal is correct not to touch this.

**Fact 5 (agents.ts domains/themes, lane-boost re-rank) — CONFIRMED exactly**, including the quoted finance example (`domains: ["budgeting", "credit optimization", "loans", "refinancing", "runway", "cashflow"]`, `agents.ts` line 135-136). The lane-boost mechanism is confirmed in full at `huddle.functions.ts` lines 2493-2523: `MEMORY_MIN_SCORE = 0.3`, `laneTerms` built from `winner.domains`/`winner.themes` (lowercased, length ≥3), `laneBoost()` adds `+0.12` for a text-keyword hit and `+0.06` for co-authorship, applied as a **sort-only** adjustment over rows already fetched by `searchChunks` — genuinely "pure re-rank, no SQL change" as CLAUDE.md itself documents ("Role-scoped retrieval... Pure reorder, no SQL change").

## 2. Is adding `domains TEXT[]` to `rag_chunks` actually additive/non-breaking?

Mechanically yes, following the exact precedent of `author_agent_ids`: `ALTER TABLE ... ADD COLUMN IF NOT EXISTS domains TEXT[] DEFAULT '{}'` plus a `GIN` index is a safe, idempotent pattern already proven in this codebase (line 138, 145-148 for chunks; 189, 198-199 for triples). It would not break `information_schema`-based checks in `runBootstrap()`'s report, and wouldn't collide with `CHUNK_DEDUP_KEY` (since domains isn't part of the identity of a chunk, correctly left out).

But it is **not** "no separate migration step" in practice: because bootstrap is explicit/manual (see above), the column won't exist until someone clicks "Run bootstrap," and every touch-point that would read/write it (`WriteChunkInput`/`ChunkRow`/`SearchChunksInput` in `rag/types.ts`, the `INSERT`/`ON CONFLICT` in `writeChunk`, the `SELECT`/mapping in `searchChunks`) needs coordinated changes across `types.ts` and `azure-pg.server.ts`, not a one-line SQL change. That's a real, multi-file, bounded change — comparable in size to the `author_agent_ids` rollout, not "just add a column."

## 3. Is extending the lane-boost re-rank to a stored tag actually small/low-risk?

The code-level lift is small (extend `ChunkRow`/`SELECT` to carry `domains`, extend `laneBoost()` to also check `domains.some(d => laneTerms.includes(d))` or similar). But there's a scoring/ranking interaction worth flagging: `MEMORY_CANDIDATE_K = 20` is a hard SQL `LIMIT` applied **before** any lane-boost re-rank runs (confirmed at `searchChunks`, line 754-771, and the comment at 2464-2469 explicitly warns "a chunk the ANN ranked 7th was unreachable no matter how relevant" — i.e., the re-rank can only reorder what the ANN vector search already put in the top 20). If the owner's ~3-page memory dump adds a meaningful number of finance-tagged (etc.) chunks, and a query from an unrelated agent happens to embed close to that content by pure semantic similarity (plausible — a family-agent question about "budget for the kids" is semantically adjacent to finance content), those chunks can occupy ANN-limited slots at the database layer, ahead of that agent's own genuinely relevant history, and the lane-boost re-rank has no way to un-crowd them because it never sees anything the ANN query didn't return. This is a real, if second-order, risk of "crowding out legitimately relevant memory for that turn" that the proposal's re-rank design cannot fix by itself — it would need either a wider `MEMORY_CANDIDATE_K` (more DB cost) or an actual scope-level filter (see next section).

## 4. Does `scope='global'` + re-rank actually achieve the "lane depth without bloat" goal? — This is the crux, and the answer is: **only partially.**

Two distinct things get conflated in "bloat": (a) prompt-token cost per turn, and (b) noise/relevance crowd-out.

- **On (a), the proposal's framing overstates the actual cost risk.** `MEMORY_INJECT_N = 8` (line 2469) caps what's actually injected into any agent's prompt per turn, regardless of how many rows sit in `rag_chunks`. Tier-1 content sitting in the DB does not itself cost tokens on every turn for every agent — only the (at most 8) chunks that win the floor+re-rank do. So "does every agent pay to retrieve/consider this content on every turn" is true only in the sense of one extra ANN query cost (already paid today, unconditionally, for every agent) — not in the sense of prompt bloat for content that never gets selected.
- **On (b), the proposal's own design is honest that it's a re-rank, not a wall — and that is a real limitation, not merely a reframing.** Because Tier 1 rows are `scope='global'` and every agent defaults to `"shared"`, **any** agent's query can retrieve and get **injected** with another lane's tagged content, provided it scores ≥0.3 and wins a slot in the top 8 after boost — the boost only privileges the *owning* agent's ranking of its *own* lane content; it does nothing to suppress a *non-owning* agent from retrieving and injecting that same content when it's simply the closest vector match available. So the proposal's stated goal — "agent-specific depth... without bloating every single agent's prompt... with everything about the owner" — is **not fully achieved** by scope=global+re-rank alone: a large finance-lane dump can still surface, unprivileged, in a non-finance agent's 8-slot injection budget on a semantically-adjacent query, precisely because there is no hard filter, only a boost that helps the owning agent win ties but does nothing for everyone else's retrieval.
- **What would actually close this:** a genuine scope-level filter analogous to today's `"private"` clause, but keyed on **domain overlap** rather than `agent_id` — e.g., a new `scopeClause` branch (or a new `SharingMode`/parameter) that does something like `scope='global' AND (domains IS NULL OR domains && $agentDomains OR scope='agent'...)`. This does not exist today (confirmed: `scopeClause`'s only branches are `"private"`/`"readonly-shared"`/default, none domain-aware) and would be genuinely new code, a real design decision (what happens to untagged legacy global rows — they'd need to stay universally visible, i.e. `domains IS NULL` must be an escape hatch), and a bigger behavior change than the proposal frames it as. The proposal should either (i) explicitly own that it's choosing "soft depth-preference, not hard lane isolation" as the design (which is a legitimate, lower-risk choice) and stop claiming it "achieves lane depth without bloat" in the strict sense, or (ii) add the hard filter if true isolation is actually wanted.

## 5. Naming/collision risk on domain strings — CONFIRMED as a live risk, with a concrete example already in the codebase.

`agents.ts` domain/theme vocabulary is free text with **no normalization layer** anywhere in `laneBoost()` beyond `.toLowerCase()` (line 2498-2500) and a `length >= 3` filter — no stemming, no synonym table, no canonical vocabulary enforcement. And the collision risk isn't hypothetical: the **family** agent's `themes` include `"school"` (agents.ts line 154) and the **education** agent's `themes` also include `"school"` (line 172) — two agents already share a live keyword. Under the current text-keyword-match boost this just means both agents get a small boost on any chunk mentioning "school," which is a soft, low-stakes ambiguity. But it directly evidences the proposal's own risk: if Tier 1 tags content with a domain string like `"education"` while an agent's own `domains` array says `"school"` (or `"budgeting"` vs. `"budget"`), a hard-match extension (`domains.includes(x)`) will silently miss it with **no warning, no fallback** — worse than the current keyword substring match, which is at least tolerant of partial text overlap. The proposal should specify: (a) a single canonical vocabulary list domains must be drawn from (ideally generated from the union of all `agents.ts` domains/themes, with validation at ingestion time), and (b) whether matching is exact-set-membership or substring-tolerant, because these have very different silent-failure profiles.

## 6. Other prompt-assembly paths that would miss Tier 1 (beyond the known voice gap)

Traced `runAgentTurn` (defined once, `huddle.functions.ts` line 2129) as the **single** function containing both the memory auto-retrieval block and the lane-boost re-rank. Confirmed it is the shared engine for:
- the sequential per-agent queue loop (line 2143's `for` loop calls into it via `runAgentTurn`/`runBounded`),
- the parallel wave-based chunked engine (`Promise.all(wave.map((id) => runBounded(id, frozenPrior)))`, line 6879, whose results are merged by `mergeAgentResult`, line 6247 — this is a result-merge function, not a second copy of the retrieval logic, so no drift there),
- mention-chain re-queues (`parseMentions`/`handoffById`, lines 6463-6475) — these just push ids back onto the same queue, which still runs through `runAgentTurn`,
- ceremony replies — `isCeremonyTrigger` (line 2453) only skips retrieval on the ceremony **kickoff** message itself; subsequent per-agent ceremony turns still run through the same `runAgentTurn` and so still get lane-boost.

So Tier 1 (if wired into this same function, which is the natural place) would reach essentially all text-chat paths, group and 1:1 alike, matching the reach the *existing* lane-boost already has — consistent with the task's suspicion that it would be "silently scoped to the same subset of paths." Confirmed two genuine misses, both **pre-existing** and **unaddressed** by this proposal (which doesn't claim to fix them, but should say so explicitly rather than leave it ambiguous):
- **Voice** (`realtime-tools.server.ts`) — confirmed above, no lane-boost, no domains, nothing.
- **Worker sub-turns** (`huddle.functions.ts` ~7060-7107) — confirmed above, zero RAG retrieval of any kind today; Tier 0 reaches it, Tier 1 would not, by construction (no `searchChunks` call exists in that path to extend).

`getLedger`/`renderLedger` (Tier 2, triples; line 2566-2567) lives inside the same `runAgentTurn` function, so it has the same reach as the chunk retrieval — consistent, not a separate gap.

## 7. An interaction the proposal doesn't mention: Tier 1's `scope='global'` choice vs. the per-agent "private" sharing toggle

Because `scopeClause("private", ...)` returns `scope='agent' AND agent_id=$AGENT` **only** (global explicitly excluded, confirmed line 492-494), an agent whose owner has flipped its "Shared memory" toggle off (a real, user-facing, currently-exposed setting per Fact 4) would lose access to **all** `scope='global'` rows — including its own lane's Tier 1 content, since Tier 1 deliberately never uses `scope='agent'`. This is a legitimate, foreseeable interaction: if the owner ever sets, say, the finance agent to "private" for genuine privacy reasons, it simultaneously and silently cuts that agent off from the finance-lane depth this whole proposal exists to deliver. Worth an explicit design note (even if the answer is "acceptable, private-mode agents forgo lane depth too" — that should be a stated choice, not a silent side effect).

## Overall verdict: SOUND WITH CHANGES

The proposal's Tier 0/2 reuse is correct and matches the code. The Tier 1 mechanism is a legitimate, low-blast-radius, precedent-following pattern (mirrors `author_agent_ids` closely) and is not going to break anything structurally. But it should not ship as currently framed without addressing:

1. **State plainly that this is a soft depth-preference, not a noise-reduction mechanism** — per §4, `scope='global'` + re-rank does not stop other agents' turns from retrieving/injecting another lane's Tier-1 content when it's the closest embedding match; it only helps the *owning* agent rank its own lane's content higher. If true cross-agent noise reduction is the actual goal (as the owner's stated motivation implies), a real filter (a domain-aware `scopeClause` branch, new code) is needed — decide and say which goal this ships for.
2. **Extend the `ON CONFLICT DO UPDATE` merge logic to include `domains`** (array union, same pattern as `author_agent_ids`) — otherwise re-running ingestion or any dedup collision silently drops domain tags (first-writer-wins, per the existing `metadata`/`embedding` precedent in the same file).
3. **Specify a canonical, normalized domain vocabulary and matching rule** before ingestion — the codebase already has a live "school"/"school" cross-agent theme overlap (family vs. education agents) and zero normalization layer; a hard-match extension will silently miss on any variant spelling.
4. **Note that `runBootstrap` is manual**, not auto-applied on deploy — the column won't exist until someone runs it from Settings, so code changes need to tolerate that ordering (or the rollout instructions need to say "run bootstrap after this deploys").
5. **State explicitly that voice and worker sub-turns remain out of scope** (both confirmed to lack any lane-boost/Tier-1 reach today, and this proposal does nothing to change that) rather than leaving it ambiguous.
6. **Decide the `private`-sharing-mode interaction** (§7) as an explicit design choice, not a silent gap.

None of these are reasons to block the proposal outright — they're scoping/precision gaps in an otherwise reasonably-designed, additive change that a competent implementer would likely hit anyway once they got into `writeChunk`'s `ON CONFLICT` clause and `scopeClause`. But "additive re-rank, no hard wall" should not be sold as solving the cross-agent noise/cost problem the owner actually described — as designed, it solves ranking-within-lane, not isolation-across-lanes.
